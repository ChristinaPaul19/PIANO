# Arranger core contract

`engine.js` exports `{ ArrangerEngine }`, a renderer-independent CommonJS EventEmitter. Construct with `{ audio }`; deterministic tests can additionally inject `now` (monotonic milliseconds), `setTimeout`, and `clearTimeout`. `state` emits serializable `snapshot()` values, on state changes and otherwise at most once per beat (below 20 Hz). No special `error` event is emitted. Validation failures set `snapshot().error` and throw; async audio failures set error and stop without rejected timer promises. `start()` reports backend failure in its returned snapshot. Successful configuration/start/import clears the prior error.

## Controls

- `configure({ enabled?, styleId?, tempo? })`: styles `pop`, `rock`, `waltz`; tempo 40–240 BPM, finite fractional values allowed. Style changes require **stopped** transport, otherwise an error is exposed. Changing style selects its default tempo unless explicitly supplied. Meter changes discard incompatible saved progression and disable looping.
- `start({ intro = false } = {})`: requires enabled arranger and ready audio. Repeated start is a no-op. Starts at bar 0, beat 0, optionally with the two-bar intro. No known chord is required: drums play while bass waits. `stop()` cancels scheduling, finishes recording, and panics **only channels 1 and 9**. Disabled configuration stops; audio loss stops without sending commands to a non-ready backend. Audio reinitialization never restarts transport.
- `requestSection('A'|'B'|'C'|'D'|'intro'|'fill'|'break'|'ending')`: latest request wins at the next bar boundary. Main variation persists. Two-bar intro and one-bar fill/break return to the selected main; two-bar ending stops. A queued request can replace an ending at its next bar. When stopped, only A–D selection is accepted; use `start({intro:true})` for intro.
- `noteOn(note)` / `noteOff(note)` only recognize chords; they do not play piano. Channel 0 remains exclusively the parent's keyboard. Bass uses channel 1, GM program 33; drums use channel 9. `clearInput()` clears held keys but **keeps the latched chord and any already recognized pending chord**.
- `snapshot()` and `exportProgression()` are synchronous detached data; other methods may be awaited. Bar and beat are zero-based; beat is the whole-beat index within the bar. During stop, the last transport position is retained; start resets it.

## Chords and quantization

Only MIDI notes 0–71 participate, and only while enabled. At least three distinct pitch classes must exactly match `major`, `minor`, `dominant7`, `maj7`, `min7`, `dim`, `aug`, `sus2`, or `sus4`. Root is a pitch class 0–11. Octave doublings and inversions are accepted. No single-note or two-note root guesses. A recognized chord latches on complete note-on input; note-off never reinterprets a releasing seventh chord as a triad. Invalid/incomplete held sets leave the previous chord intact. While running, recognition becomes effective on the **next whole beat**, never midway through a beat.

Augmented chords have three equivalent roots; sus2 and sus4 share pitch-class sets. Disambiguation prefers the prior exact chord, then prior root, then the lowest held note's pitch class, then ascending root / declared quality order. This is deterministic, not a claim to infer harmonic intent from inherently ambiguous inversions. All unambiguous inversions are recognized without prior context.

## Recording and looping

`recordStart()` requires running transport and looping disabled. It arms recording at the **next bar**, with UI `recording:true` immediately. Repeated calls do not restart recording. Changes record at whole-beat offsets from that boundary; the first known chord is included, with no fabricated chord during initial silence. `recordStop()` / transport stop finalize a whole-bar length rounded upward, at least one bar; stopping before the armed boundary yields an empty one-bar recording. Recording automatically finishes at 128 bars. At most 512 events are retained, with adjacent duplicate chords collapsed.

Persistence schema: `{version:1, beatsPerBar:3|4, lengthBars:1..128, events:[{beat,root,quality}]}`. Beat offsets are increasing unique nonnegative integers strictly below the loop length. Root is 0–11; quality uses the list above. Empty events and a delayed first chord are valid. `importProgression(document)` requires stopped transport and matching meter, rejects unknown fields/prototypes/accessors/invalid values/oversized arrays, clones validated data, and leaves the previous document intact on failure. No filesystem paths or shell commands occur in this schema; local save/load belongs to the parent.

`setLoop(true)` requires a finished progression. When stopped, the next start plays from position 0; when running, playback starts from position 0 at the **next bar**, with `looping:true` reporting armed state immediately. Every loop resets to no chord before the first event, so silence does not inherit an old chord. Live input is tracked but cannot replace loop chords. `setLoop(false)` re-enables recognition of currently held notes, applying a valid held chord at the next beat (immediately if stopped). Invalid held notes preserve the last latch. Stop preserves the loop flag for the next start.

## Timing and safety

The monotonic transport uses absolute sixteenth-note deadlines, not renderer timers and not completion-relative sleeps. Live tempo changes preserve the fraction of the next subdivision remaining. Scheduling awaits each tick's audio commands; no concurrent ticks or unbounded command backlog. Lateness beyond eight subdivisions (two beats) safely stops instead of bursting through missed bars. Every note has an explicit note-off; repeated same-pitch strikes first release the earlier note. Scoped channel panic additionally handles interruption, ending, disabled configuration and backend failures. Generation checks prevent canceled startup/ticks from restarting scheduling. Patterns are original, explicit and distinct for all three styles and all A–D sections, with dedicated intro/fill/break/ending recipes.

Validation: `node --test test\arranger-core.test.js test\arranger-waveform.test.js` and `node scripts\verify-arranger.js`. The latter uses the actual configured AudioEngine/FluidSynth file driver, writes only `verification\arranger`, and analyzes isolated drum/bass and ensemble PCM plus C/D bass fundamentals. It shuts down only the AudioEngine processes it creates.

Waveform analysis uses 128 ms Hann windows with a 32 ms hop, averaging spectral **powers** before taking the square root. A coherent Fourier sum across an entire bar is unsuitable: phase resets between repeated bass attacks can cancel the actual root fundamental, especially Rock's eighth-note retriggers. Synthetic regressions cover opposite phases, attack transients, leading silence and timing jitter, and ensure silence/wrong roots do not pass. Root discrimination still requires the expected magnitude to exceed the other root by a factor of 1.15. Energy and final-tail silence are measured in the WAV sample domain, not by assuming that AudioEngine initialization completion corresponds to sample zero. Reports identify the estimator, frequency probes, frame count and windows. This verifies spectral content, not sample-accurate MIDI timing; host scheduling, command acknowledgment and file-driver startup retain their normal jitter/latency.
